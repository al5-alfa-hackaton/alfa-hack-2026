# Мониторинг качества

Как команда проверяет, что лента и ответы остаются точными, персональными и недорогими. Здесь описано, что измеряем, откуда берем данные, как часто смотрим и что делаем, если метрика просела.

## Что измеряем

| Уровень | Метрика | Источник | Цель |
| --- | --- | --- | --- |
| **Контент** | Точность цитат — доля фактов и позиций банка, найденных в документе дословно | `eval:answers`; в работе — `gateDraft` | ≥ 98% |
| | Вывод ИИ выдан за позицию банка: текст ссылается на оценку Альфа-Банка без проверенной цитаты материала банка | `eval:answers`, экспертная проверка | 0 |
| | Числа без источника в выводах и ответах | `eval:answers` | ≤ 1 на 10 карточек |
| | Фактические ошибки и необоснованные выводы | экспертная проверка | ≤ 5% карточек |
| | Заполненность карточки: главное, риск или возможность, шаг | `eval:answers` | ≥ 90% |
| **Персонализация** | P@3 и строгая P@3 — доля связанных с компанией новостей в первых трех | `eval:ranking` | P@3 ≥ 70% и не ниже правил на отложенной выборке |
| | R@5 — доля связанных новостей пула, попавших в топ-5 | `eval:ranking` | не ниже прошлого отчета |
| | nDCG@5 — прямые новости выше косвенных | `eval:ranking` | ≥ 0,6 |
| | Метрики по ролям: финансовый и генеральный директор отдельно | `eval:ranking` | ни одна роль не ниже 60% P@3 |
| | Совпадение топ-3 с другими компаниями | `eval:ranking` | ≤ 50% |
| | Доля оценок «полезно» среди оцененных карточек | `insight_user_states.feedback` | ≥ 70% |
| **ИИ-компоненты** | Доля опубликованных карточек и пропусков агентом | `eval:answers`, `analysis_runs` | публикация ≥ 85% |
| | Форма ответа на вопрос: N предложений, список, кратко, приветствие, уточнение | `eval:answers` | ≥ 80% |
| | Повтор между ответами на разные вопросы | `eval:answers` | ≤ 0,3 |
| | Время запуска p50 / p95, ожидание в очереди | `analysis_runs`, `run_events` | лента p95 ≤ 60 с, очередь p95 ≤ 10 с |
| | Доля ошибок, повторов и отмен запусков | `analysis_runs.status`, `analysis_runs.attempt` | ошибок ≤ 2% |
| | Стоимость запуска и за сутки | `eval:answers`, `daily_budgets.spent` | лента ≤ 1 ₽, сутки ≤ 70% лимита |

Цели — стартовые: выставлены по первому прогону (результаты в `packages/agent/results/`) и пересматриваются раз в месяц.

## Откуда данные

1. **Офлайн-наборы** в `packages/agent/eval/`:
   - `ranking-set.json` — 6 компаний, на которых подбирались веса отбора;
   - `ranking-holdout.json` — 6 компаний из других отраслей (овощи, сыр, металлопрофиль, приборы, софт, гостиница). При настройке не используются. Если на них метрики заметно ниже, отбор подогнан под примеры;
   - `questions.json` — компании ленты, отложенные компании и 8 вопросов разной формы.

   У каждой новости в наборе есть оценка 0/1/2 и роль, для которой она важна.
2. **Журналы сервиса** в Postgres: запуски и их статусы, события шагов, вызовы модели, траты за сутки, оценки и комментарии пользователей к карточкам, переписка по карточкам.
3. **Экспертная выборка**: случайные карточки и ответы из работы сервиса, которые проверяет аналитик банка.

## Как часто

**На каждое изменение** модели, промпта, отбора, разметки или корпуса:
- `pnpm --filter @alfa/agent eval:ranking` (бесплатно);
- `pnpm --filter @alfa/agent eval:answers` (~8 ₽).

Новый отчет сравниваем с прошлым из `results/`. Изменение не принимается, если выполняется хотя бы одно:
- точность цитат упала;
- появился вывод ИИ, выданный за позицию банка;
- P@3 на отложенной выборке опустилась ниже правил.

В отчете фиксируются версии промпта (`PROMPT_VERSION`), отбора (`ML_RANKING_VERSION`) и разметки (`NEWS_TAG_PROMPT_VERSION`).

**Ежедневно** — `pnpm monitor:report [ГГГГ-ММ-ДД]`. Команда читает журналы Postgres (`DATABASE_URL` из `projects/backend/.env`) и пишет отчет в `data/processed/monitor/` (вне git: в нем комментарии пользователей). В отчете:
- число запусков;
- ошибки и отмены;
- p50/p95 времени и очереди;
- траты против лимита;
- доля ответов «Подтверждённых данных недостаточно»;
- новые оценки «не полезно» с комментариями.

**Еженедельно** — экспертная проверка 20 случайных карточек и 10 ответов на вопросы. Для каждой эксперт отмечает:
- верны ли факты;
- обоснован ли вывод для этой компании;
- правильно ли разделены позиция банка и вывод ИИ;
- полезность от 1 до 5.

Отдельно разбираем все карточки с оценкой «не полезно». Каждая найденная ошибка становится примером в наборе: новость с оценкой — в `ranking-*.json`, вопрос — в `questions.json`. Так следующий прогон ловит ее автоматически.

**Ежемесячно:**
- доразмечаем пул: новости, которые новый отбор поставил в топ-5, а в наборе их нет («Не размечено» в отчете);
- добавляем в отложенную выборку одну-две новые отрасли;
- пересматриваем цели по накопленным оценкам пользователей и экспертов.

## Обратная связь пользователей

В карточке уже есть оценка «полезно / не полезно» и комментарий. Сигналы:
- доля «полезно» — отдельно по ролям и отраслям;
- комментарии к «не полезно» — разбираются еженедельно;
- сохранение карточки;
- переход к первоисточнику;
- повторный вопрос с тем же смыслом — значит, ответ не понят.

Низкая доля «полезно» по одной отрасли — повод добавить ее компании в набор и проверить отбор. Низкая доля по одной роли — повод проверить метрики по ролям.

## Кто отвечает

- **Агент и наборы оценки** (`packages/agent`): прогоны при изменениях, доразметка, отчеты.
- **Отчет по журналам сервиса**: `scripts/monitor-report.mts`. Код бэкенда он не меняет, только читает базу. При изменении схемы базы запросы в нем нужно обновить.
- **Эксперт банка**: еженедельная проверка и выборочная проверка разметки. Сейчас оценки в наборах поставил ассистент, их нужно подтвердить.
